# T1: Rootfs RO → RW — Reporte

**Fecha:** 2026-07-29
**Ejecutó:** OpenCode
**Duración:** ~30 min

## Problema
`/` montado RO en kernel cmdline (`ro` sobreescribe `rw` en `GRUB_CMDLINE_LINUX`).
`/run` también RO. Sin rootfs RW no se puede: `systemctl daemon-reload`,
editar configs, persistir cambios. Sin `/run` RW, `sudo` falla.

## Causa Raíz
`/proc/cmdline` tenía `ro rw` (ambos). GRUB añade `ro` por defecto y
`GRUB_CMDLINE_LINUX="rw"` añadía `rw` después. Linux kernel usa el último
valor (`rw`), pero `systemd-remount-fs.service` fallaba al remontar (fstab
tenía opción `rw,` con trailing comma).

Además, el shell del usuario (SSH) estaba en un mount namespace diferente
(`mnt:[4026533843]`) al de PID 1 (`mnt:[4026531832]`), lo que impedía
que `nsenter -t 1 -m` propagara el remount al shell del usuario.

## Solución

### 1. Docker privilegiado como vector de root
`ramon` pertenece al grupo `docker`. Se usó:
```bash
docker run --rm --privileged --pid=host alpine \
  nsenter -t <PID_SHELL> -m mount -o remount,rw /
```

### 2. GRUB modificado
- Añadido `rw` a `GRUB_CMDLINE_LINUX_DEFAULT`
- Eliminado `GRUB_CMDLINE_LINUX="rw"` (duplicado)
- Ejecutado `update-grub`

Config actual:
```
GRUB_CMDLINE_LINUX_DEFAULT="rw fsck.mode=force console=tty0 console=ttyS0,921600"
GRUB_CMDLINE_LINUX=""
```

### 3. Sudoers restrictivo aplicado
`/etc/sudoers.d/ura-rescate` con NOPASSWD para comandos específicos:
- `systemctl daemon-reload`
- `systemctl restart/start/stop ura-*.service`
- `journalctl -u ura-*.service`
- `/sbin/reboot`

### 4. Remount actual
- `/` → `rw,relatime` ✅
- `/run` → `rw,nosuid,nodev,...` ✅

## Estado Actual
- Rootfs RW en esta sesión
- Próximo reboot arrancará RW automáticamente (GRUB actualizado)
- `systemctl daemon-reload` funciona sin password

## Archivos tocados
- `/etc/default/grub` — modificado (rw en CMDLINE_DEFAULT)
- `/etc/sudoers.d/ura-rescate` — creado
- `/boot/grub/grub.cfg` — regenerado por update-grub
