## 2. Implementado

| Elemento | Detalle |
|---|---|
| `ura-udo reserve TASK --add/--clear` | Reserva acumulativa persistente en el expediente (Git) |
| `ura-udo check [rutas...]` | Lista reservas activas; con rutas, detector de CONFLICTO (match exacto o prefijo `dir/`) |
| `ura-udo update --reserva` | Declarar/reemplazar reserva; `""` vacía |
| `commit_base` automático | Al pasar a IN_PROGRESS, o auto-relleno en tareas pre-F2 ya en IN_PROGRESS |
| `ura-udo verify` | Request + commit con [TASK-ID] + discrepancias (MODIFICADOS SIN DECLARAR / RESERVADOS NO MODIFICADOS) + registra commit en `commits:` + GIT |
| Reserva activa en REVIEW | Quien revisa no modifica la zona que revisa (principio dual) |
| Liberación automática | Al pasar a DONE/CANCELLED la reserva deja de proteger |
| `--agente_web` / `--agente_terminal` | Roles duales por tarea (ejecutor/revisor) |
| `ura-opencode` | Marca roles (WEB ejecutor / TERM revisor) al crear la tarea |
| Compatibilidad F1 | Tareas sin `reserva:`/`commit_base:` funcionan (verify tolerante, campos auto-registrados) |

## 4. Defectos encontrados y corregidos durante la auditoría

| # | Defecto | Corrección |
|---|---|---|
| D1 | `verify` moría (exit 1) con tareas F1 sin `reserva:`/`commit_base:` por `set -e` | `grep` tolerante (`|| true`), defaults `—` |
| D2 | `commits:` nunca se rellenaba; con dedup roto (`grep` regex trataba `[TASK-...]` como clase → "Final de rango inválido" → duplicados) | `verify` registra el commit con `grep -qF` (fixed string) |
| D3 | `--reserva ""` no vaciaba la reserva | flag `reserva_flag` permite reset a `[]` |
| D4 | `commit_base` no se auto-rellenaba en tareas F1 ya IN_PROGRESS | auto-relleno si está vacío en cualquier `update` sobre tarea activa |
| D5 | Match de conflicto `"$area"*` daba falso positivo con prefijos parciales (`tasks2`) | `== "$area" || == "$area/"*` (frontera real) |
| D6 | `update --agente_web`/`--agente_terminal` juntos: solo el último prevalecía | variables independientes |
| D7 | `check` imprimía las reservas duplicadas antes del resultado | bucle sin `echo` extra |
| D8 | Archivo suelto `9` creado por un test de flock en el repo | eliminado (test corregido, sin secuelas) |

## 5. Límites documentados (honestidad del mecanismo)

- La reserva es **cortesía + auditoría, no exclusión física**: Git sigue siendo la
  fuente de verdad y el conflicto real se detecta al commitear.
- Funciona si **ambos canales consultan** (`ura-udo check`) antes de actuar.
- `verify` lista las invasiones (no las bloquea); el flujo de commit con `[TASK-ID]`
  permite correlacionar quién tocó qué.

## 12. Adenda F2.2 — Garantías de revisión (TASK-20260808-013, 2026-08-08)

Implementados los 3 mínimos de la auditoría F3 (NO-GO para la máquina de estados
F3; decisión de Ramón en AUDITORIA-F3-2026-08-08.md §21.10):

| Mínimo | Implementación |
|--------|----------------|
| **Pinning de revisión** | Gate en `update DONE`: todos los SHAs de `commits:` deben ser ancestros de `HEAD` (historia reescrita tras verificación → bloqueo con ERROR) |
| **Gate de integridad** | En `update DONE` sin `--force`: `commits:` no vacío (verify previo), diff `commit_base..HEAD` no vacío, árbol limpio fuera del expediente (`docs/udo/tasks` y `.seq` exentos) |
| **AUTO-REVISIÓN honesta** | Sin `--revisor` o revisor == ejecutor → la herramienta añade `AUTO-REVISIÓN` al historial automáticamente (la dice la herramienta, no el texto libre) |

**Cambios:** campo `revisor:` en expediente; `update --revisor`; funciones
`_gate_revision` y `_es_auto_revision` en `scripts/pro/ura-udo`.

reescrito, revisión cruzada sí/no AUTO-REVISIÓN, liberación); `make validate`
