## CAPA 2 — Razonamiento con herramientas (Tool Use)

**Objetivo**: El LLM puede llamar a herramientas del sistema (make validate, git log, grep, pytest) y auto-corregir antes de entregar resultados.

**Análisis previo obligatorio**:
- ¿Qué herramientas existen hoy en scripts/pro/ que el LLM podría invocar?
- ¿Qué formato de "function calling" soportan los modelos actuales (qwen3-coder:30b, qwen3.6:27b)?
- ¿Ollama soporta tool use nativo o necesitamos parseo manual?

**Implementación propuesta**:
- Crear `motor/core/tools/registry.py`: registro de herramientas disponibles (make, git, grep, pytest, ollama list, etc.)
- Crear `motor/core/tools/executor.py`: ejecuta la herramienta, captura output, lo devuelve al LLM
- Modificar `motor/core/llm/ollama.py`: detectar cuando el LLM pide una herramienta, ejecutarla, inyectar el resultado en el contexto
- Ejemplo de flujo: "Ejecuta smoke test" → LLM genera tool_call → se ejecuta `make validate` → resultado inyectado → LLM responde con veredicto

**Criterio de éxito**:
- [ ] El LLM puede ejecutar `make validate` y leer el output sin intervención humana
- [ ] El LLM puede hacer `git log --oneline -5` y responder preguntas sobre commits
- [ ] Timeout de ejecución: 30s máximo por herramienta
- [ ] Sin sudo, sin rm -rf, sin escritura fuera del repo (sandbox)

## CAPA 3 — Memoria compartida entre agentes

**Objetivo**: Kimi (Mac), OpenCode Web (ASUS), OpenCode Terminal (ASUS) leen y escriben en el mismo log de sesiones. Cuando uno commitea, los otros lo ven.

**Análisis previo obligatorio**:
- ¿TASK-20260823-005 (log de sesiones) está implementado y funcionando?
- ¿Qué formato tiene el log (JSONL, markdown, otro)?
- ¿Cómo se sincroniza entre Mac y ASUS (Git, API, archivo compartido)?

**Implementación propuesta**:
- Extender `motor/core/sesion_logger.py` para que cada agente se identifique (kimi, web, term)
- Crear `scripts/pro/ver_sesion.py --agente web --ultimas 5` para consultar lo que hizo otro agente
- En `motor/core/prompt_system.py`, inyectar automáticamente: "Última acción de [otro agente]: ..."
- Regla: cada commit genera una entrada en el log con SHA, agente, descripción

**Criterio de éxito**:
- [ ] Al iniciar una sesión, el agente "sabe" qué hizo el último agente que trabajó
- [ ] No hay duplicación de trabajo entre agentes
- [ ] El log es la fuente de verdad, no la memoria del agente

## CAPA 4 — Predicción de intención

**Objetivo**: El sistema detecta patrones en el comportamiento de Ramón y anticipa acciones.

**Análisis previo obligatorio**:
- ¿Cuántas sesiones tenemos logueadas (mínimo 50 para patrones significativos)?
- ¿Qué tipo de patrones son predecibles (post-refactor → smoke test, post-TASK → revisión, etc.)?

**Implementación propuesta**:
- Crear `scripts/pro/patron_analyzer.py`: lee el log de sesiones, extrae secuencias frecuentes
- Ejemplo de patrón: "Tras cerrar TASK de tipo refactor, el 73% de las veces Ramón pide smoke test"
- En `motor/core/prompt_system.py`, si se detecta un patrón activo, sugerir: "¿Ejecuto smoke test o paso a la siguiente tarea?"

**Criterio de éxito**:
- [ ] Al menos 3 patrones detectados con frecuencia >60%
- [ ] Las sugerencias son útiles (Ramón las acepta >50% de las veces)
- [ ] No es intrusivo: pregunta, no ejecuta solo

## CAPA 5 — Compresión semántica del historial

**Objetivo**: El contexto crece sin fono. Las sesiones de hace 6 meses se resumen en "memoria de alto nivel" (aprendizajes, no detalles).

**Análisis previo obligatorio**:
- ¿Qué tamaño tiene el log de sesiones hoy?
- ¿Cuántos tokens consume inyectar el historial completo?
- ¿Qué modelo usar para resumir (qwen3.6:27b es suficiente)?

**Implementación propuesta**:
- Crear `scripts/pro/comprimir_historial.py`: lee sesiones antiguas (>30 días), genera resumen semántico
- Guardar resúmenes en `docs/udo/memoria/alto_nivel/YYYY-MM.md`
- En `prompt_system.py`, inyectar resúmenes de alto nivel en vez de sesiones individuales antiguas
- Ejemplo: "Agosto 2026: Se migró el router de modelos, se implementó el log de sesiones, se limpió 172 GB de huérfanos"

**Criterio de éxito**:
- [ ] El contexto inyectado no supera los 4000 tokens nunca
- [ ] Los resúmenes preservan decisiones importantes (ADRs, lecciones)
- [ ] Las sesiones recientes (<7 días) se mantienen en detalle

## CAPA 6 — Evaluación automática de calidad

**Objetivo**: El sistema ajusta su propio comportamiento en función del historial de éxito.

**Análisis previo obligatorio**:
- ¿Qué métricas de "éxito" tenemos hoy (tests pasan, sin rollback, tarea cerrada en <3 iteraciones)?
- ¿Dónde se guardan esas métricas (coordination.json, Git, log)?

**Implementación propuesta**:
- Crear `motor/core/quality_tracker.py`: lee el log y coordination.json, calcula métricas por agente/modelo
- Métricas: tasa de éxito (cerrado sin rollback), tiempo medio de cierre, iteraciones por tarea
- Ajuste automático: si un modelo tiene tasa de éxito <50%, el router lo degrada en la lista de fallback
- Reporte semanal: `scripts/pro/reporte_calidad.py` genera markdown en `docs/udo/quality/`

**Criterio de éxito**:
- [ ] Métricas calculadas para las últimas 50 tareas
- [ ] El router ajusta fallbacks en función de la tasa de éxito
- [ ] Reporte semanal generado automáticamente
